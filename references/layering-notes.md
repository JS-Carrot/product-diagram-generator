# 分层说明怎么写

图回答「谁在什么时候做了什么」或「系统由哪几层组成」。说明回答的是图上看不到的那部分：**谁对结果负责、哪一步不能自动化、哪条分支其实不回流、哪个边界没人管。**

> **核心原则：只讲图上看不出来的信息。** 把箭头复述一遍，等于什么都没写。

流程图和架构图各有一套四段，别套错。

---

## 甲、流程图版（泳道图 / 主干图 / 状态机 / 时序图）

### 一、角色层：谁对结果负责

- 每个角色一句话讲清职责边界
- 标出**唯一责任方**：每个关键结果（退款到账、设备出库、工单关闭）只能有一个角色负最终责任
- 标出**无责任方**：流程里出现但从不对结果负责的角色（纯通知方），明确写出来

```text
客户：发起换机、签收、寄回旧机，不参与检测判定。
运维：受理、出库、入库检测，对「设备可交付」负最终责任。
物流承运商：只负责运输与签收回执，不对设备状态负责。
平台系统：计费切换、逾期计时、工单关闭，对「钱和单据」负最终责任。
```

### 二、流程层：主干与分支的关系

- 主干几步、经过几个交接点
- 每条异常从哪一步岔出、**回到哪一步 或 终止**
- 标出**并行点**（同一时刻多个角色可同时动作）与**同步点**（必须等齐才能继续）

```text
主干 11 步，4 个跨角色交接点：客户→平台、平台→运维、运维→物流、物流→客户。
E1 缺货从「库存校验」岔出，客户接受替代则回到「锁定出库」，否则终止。
E2 逾期从「寄回旧机」岔出，不终止，停留在原节点持续计费。
E3 检测不合格从「入库检测」岔出，走维修工单，处理完终止，不回主干。
无并行点：签收必须先于计费切换。
```

### 三、系统层：哪个系统真在干活

- 区分**人做的动作**与**系统自动做的动作**
- 标出跨系统调用：谁调谁、靠什么触发（定时任务 / 消息 / 同步接口）
- 标出**系统边界**：哪些环节必须人工介入，为什么不能自动化

```text
自动：逾期计时由平台定时任务每日跑批，不需要人。
人工：入库检测需实物核验，由运维执行，不可自动化。
跨系统：平台 → WMS 出库单，通过换机工单号同步触发。
边界：计费规则在平台侧算，物流系统不接触金额。
```

### 四、边界与缺口：还差什么

- 图上**没画、但真实存在**的风险点
- 不确定的一律列成「待确认」，不写成结论

```text
未覆盖：多台设备同时换机时的库存抢占。
未覆盖：检测不合格后维修期间，客户是否继续计费。
待确认：7 天寄回期限是否含节假日。
待确认：旧机数据擦除失败时，谁承担合规责任。
```

## 乙、架构图版（分层架构图）

### 一、分层逻辑：为什么这么切

- 每层一句话：这层负责什么、不负责什么
- 讲清**切分依据**（本技能的默认依据是「规则归谁」，见 diagram-selection 第六节）

```text
触点层：两个入口，客户侧只发起与查看，运维侧才审核与处置。
应用服务层：只编排，不写规则——改规则不动页面，改页面不碰规则。
核心业务域：六个域各自持有状态机，域间只通过事件通信。
中台与集成层：七个能力都是别人的系统，本平台只接不算。
基础与数据层：只存事实，不做判断。
```

### 二、依赖与数据流

- 主依赖方向是什么，有没有反向依赖（有就必须单独说明）
- 关键数据流走哪条线（如「计量结果供计费域消费」）
- 哪一层是瓶颈或单点

### 三、边界：哪些不是这套系统

- 明确写出**不属于本系统**的部分，避免评审时被追问
- 标注需要人工或线下处理的环节

```text
WMS、物流轨迹、车联网接入均为外部系统，本平台只做对接与展示。
设备维修为线下流程，系统只记录工单状态。
```

### 四、已定稿与待确认

- 把「已定稿」的结论列出来（与图上决策带一致），防止重复讨论
- 把「待确认」的列出来，标清缺少哪个角色拍板

## 写作要求

| 要求 | 说明 |
|---|---|
| 短句 | 一句话说一件事，别堆长定语 |
| 具体 | 写「7 天」「换机工单号」，不写「一段时间」「相关单据」 |
| 有主语 | 写「平台定时任务触发」，不写「被触发」 |
| 不复述箭头 | 图上已有的连边不重复描述 |
| 不编造 | 素材里没有的结论一律进「待确认」 |
| 篇幅 | 四段合计 200–400 字。超过 500 字，说明图没画清楚 |

## 交付格式

```markdown
## 分层说明

### 角色层
...

### 流程层
...

### 系统层
...

### 边界与缺口
...
```

放在源码同一个 Markdown 文件里，**图在前、说明在后**。
